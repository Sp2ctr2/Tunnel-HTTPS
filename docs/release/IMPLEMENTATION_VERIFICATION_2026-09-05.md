# Tunnel HTTPS 구현·검증 기록 — 2026-09-05

대상: `TunnelHTTPS_Competition_WORKING_COPY/project`.

이 문서는 과거의 “코드 완료” 보고서와 이번 실행 검증을 구분한다. 단위 테스트 통과, 실제 Android TUN 통과, 배포 준비 완료는 서로 다른 판정이다. 정식 서명이나 물리 기기 검증 없이 모든 환경에서 완벽하다고 주장하지 않는다.

## 프로젝트가 실제로 하는 일

이 앱은 원격 서버로 트래픽을 보내는 일반적인 상용 VPN이 아니라 Android `VpnService`를 이용하는 **기기 내부 패킷 처리 앱**이다. 공인 IP나 접속 국가를 바꾸지 않는다. HTTPS를 복호화하지 않으며, HTTP 등 비TLS 트래픽을 목적지까지 새롭게 암호화하는 서비스도 아니다.

주요 처리 순서는 다음과 같다.

1. WebView의 로컬 화면이 제한된 네이티브 브리지로 설정·연결 명령을 전달한다.
2. 서비스가 동의·VPN 권한·설정을 확인하고 TUN 인터페이스를 만든다.
3. IPv4/IPv6 패킷을 검증·정규화한다. 조각난 패킷은 제한된 메모리 안에서 재조립한다.
4. DNS는 로컬 정책 검사와 암호화 DNS 경로로, TCP·UDP는 각 릴레이로 보낸다.
5. 상위 소켓은 VPN에서 제외하고 선택한 실제 네트워크에 연결한다.
6. 응답은 체크섬과 필요한 IP 조각을 생성한 뒤 제한된 TUN 출력 큐로 전달한다.

FAST/BALANCED/STRONG 이름을 서로 다른 보안 프로토콜이나 서로 다른 원격 VPN 서버처럼 해석해서는 안 된다. 현재는 호환성 프리셋이며, Turbo의 도달성 검사는 기저 네트워크 검사다. 앱 자체의 진단 요청이 성공했다는 이유만으로 다른 앱의 TUN 경로가 정상이라고 판단해서도 안 된다.

구성 요소별 책임과 상세 호출 순서는 [아키텍처 문서](01_ARCHITECTURE_AND_VPN_FLOW.md)에 있다.

## 수정 내용과 이유

### IPv4 대용량 UDP

기존 APK에서 60,000바이트 UDP 에코가 타임아웃으로 재현됐다. VPN을 끈 동일 에뮬레이터에서는 정상 왕복했다. 문제는 한 곳이 아니었다.

- 수신 IPv4 조각을 공통 처리 경로 앞에서 재조립하지 않았다.
- 재조립을 추가한 첫 수정본도 실패했다. UDP 릴레이가 재조립된 패킷을 일반 패킷으로 취급해 TUN MTU 초과로 버렸다.
- 큰 UDP 응답도 TUN MTU에 맞는 IPv4 조각으로 만들어야 했다.

`Ipv4PacketNormalizer`와 `Ipv4PacketFragmenter`를 추가하고, 정상적으로 재조립됐다는 정보를 UDP 릴레이까지 전달했다. 단순히 모든 패킷의 MTU 제한을 해제하지 않았다. 일반 패킷에는 기존 크기 제한이 적용되며, 재조립된 IPv4 UDP 페이로드의 상한은 65,507바이트다.

보안·자원 제한은 다음과 같다.

- IPv4 헤더 길이·전체 길이·체크섬과 지원 가능한 옵션 검증.
- 불완전한 전송 계층 헤더, 모순되는 마지막 조각, 겹치는 조각 거부.
- 조각 식별자에 대한 제한된 거부 기록으로 혼합 재조립 방지.
- 최대 64개 재조립 문맥, 2MiB 보관 데이터, 60초 고정 만료 시간.
- 일반 패킷은 조각용 주소 키·페이로드 복사를 만들지 않는 별도 경로 사용.
- 응답 조각의 IPv4 헤더 체크섬 재계산. DF가 설정된 과대 패킷을 임의로 조각내지 않음.

실제 정상화→루프백 UDP 소켓→응답 조각화→재조립의 통합 테스트에서 길이, 주소, 포트, IP/UDP 체크섬과 전체 페이로드를 확인한다.

### IPv6·실제 네트워크 선택·DNS

VPN이 기본 네트워크가 된 뒤에도 실제 Wi-Fi/셀룰러 네트워크를 추적하도록 비VPN 네트워크를 선택한다. API 31 이상은 best-matching callback, 이전 API는 해당 비VPN 네트워크 요청 경로를 사용한다. 이를 위해 범위가 좁은 `CHANGE_NETWORK_STATE` 권한을 추가했다.

보호된 상위 TCP/UDP 소켓은 선택된 실제 `Network`에 바인딩한다. 네트워크 교체와 바인딩이 겹치면 이전 문맥을 사용한 소켓을 성공으로 인정하지 않는다. 단순한 신호 세기·capability 갱신만으로 정상 흐름과 DNS 연결을 전부 초기화하지는 않는다.

DoH 제공자의 부트스트랩은 지정된 IP 후보를 우선 사용한다. 정상 경로에서 제공자 이름을 동기식 시스템 DNS로 먼저 조회하지 않는다. IPv6 전용 문맥에서는 native IPv6와 제한된 NAT64 후보를 사용한다. DNS 서버 주소가 우연히 같아도 실제 네트워크가 달라졌다면 이전 네트워크의 진행 중 질의를 취소한다.

IPv6 UDP에서는 재사용 버퍼의 용량과 실제 패킷 길이를 혼동하던 처리를 수정했다. 유효한 짧은 패킷을 큰 패킷으로 잘못 판단하지 않는다. 기존 IPv6 재조립·체크섬·DNS64/NAT64 회귀 검사는 계속 유지한다.

### TCP·QUIC·응답 전달

TCP 서버가 EOF를 보냈더라도 클라이언트 수신 윈도에 FIN을 넣을 공간이 없으면 기다린다. 수신 윈도 밖으로 FIN을 보내 반쪽 종료나 느린 수신이 멈추는 상황을 방지한다.

QUIC v1/v2 Retry는 구조만 보는 대신 Retry integrity tag를 검증한다. 임의의 UDP/443 데이터나 손상된 Retry를 성공적인 QUIC 경로의 증거로 사용하지 않는다.

UDP 유휴 흐름 정리와 송신이 겹치는 경쟁 상태, 네트워크 초기화와 응답 전달이 겹치는 경쟁 상태를 별도로 다룬다. 네트워크 세대와 소켓 세대가 바뀐 뒤에는 이전 응답 조각과 도달성 콜백을 새 경로의 결과로 게시해서는 안 된다. 출력 게이트는 한 패킷 단위로 사용해 초기화가 전체 조각 묶음의 출력 대기를 기다리지 않도록 한다.

### 서비스 수명주기와 UI

서비스 시작·종료·설정 갱신·네트워크 초기화의 무거운 작업을 메인 스레드에서 분리했다. 포그라운드 서비스 승격은 즉시 수행하고, 자원 변경은 순서대로 처리한다.

서비스 인스턴스와 연결 세대를 구분한다. 이전 인스턴스의 종료가 새 인스턴스의 알림·상태를 지우지 않도록 하며, 이미 폐기된 시작 작업이 설정·Turbo 상태를 늦게 덮어쓰지 않도록 한다. 인스턴스 간 엔진 작업도 메인 스레드 밖에서 직렬화해 늦은 이전 `establish()`가 새 TUN을 무효화하는 경우를 막는다. 설정 변경 실패 시에는 기존 설정·진단 상태로 돌아가는 경로를 유지한다.

UI에서는 연결 중 앱·도메인 목록 변경도 실제 설정 갱신으로 이어지게 했다. Turbo가 설정에서 켜져 있다는 이유만으로 연결되지 않은 화면에 ACTIVE를 표시하지 않는다. 실제 UI 스크립트를 Node VM에서 실행해 표시 상태와 연속 설정 갱신 큐를 검사한다.

릴리스에서는 WebView 디버깅도 명시적으로 비활성화한다. Android의 [공식 API 문서](https://developer.android.com/reference/android/webkit/WebView#setWebContentsDebuggingEnabled(boolean))는 비디버그 앱의 기본값을 꺼짐으로 설명하지만, 이번 에뮬레이터는 `ro.build.type=userdebug`였다. Chromium의 [OS 디버그 빌드 처리 코드](https://chromium.googlesource.com/chromium/src/+/9963b4a7d5d60e3c270bb880a7350447c570656e/android_webview/glue/java/src/com/android/webview/chromium/SharedStatics.java)에는 해당 OS에서 공개 비활성화 요청을 무시하는 경로가 있다. 따라서 이 환경에서 관찰한 DevTools 접속점은 비디버그 APK 플래그만으로 판정할 수 없다. 일반 사용자용 OS에서 접속점이 닫혀 있는지 확인하는 배포 검사를 별도로 유지한다.

### Turbo 상태 검사

기존 상태 검사는 IPv4에만 의존하는 TCP 후보와 단일 DNS 주소를 사용하는 HTTPS 연결 때문에 실제 릴레이가 정상이어도 실패 상태를 표시할 수 있었다. 지정된 IPv4·IPv6 후보와 NAT64 후보를 제한된 수 안에서 번갈아 시도하도록 바꿨다. 선택한 실제 네트워크를 사용하며 TLS 인증서·호스트 이름 확인은 유지한다.

TCP 연결만 됐다는 이유로 ACTIVE로 승격하지 않는다. HTTPS 확인도 성공해야 한다. 상태 줄 읽기에는 절대 시간 제한을 두며, 중단된 검사는 다음 후보를 계속 시도하지 않는다. 이 검사는 연속적인 인터넷 품질 보증이나 TUN 전체의 성공 증명이 아니다.

주소 후보 수정 후에도 Android 실행에서는 상태 검사 실패가 남았다. 별도 검사 앱의 직접 TLS 연결은 세 제공자 모두 인증서 검증과 HTTP 응답에 성공했다. 본 앱에 추가한 제한된 단계별 진단은 TLS 이전의 `protect-bind` 실패를 가리켰다. TCP 검사와 DoH 소켓은 옵션 설정 또는 bind로 내부 소켓을 준비한 뒤 보호했지만, HTTPS 검사만 생성 직후의 소켓을 그대로 보호하고 있었다. HTTPS 검사도 소켓 옵션을 먼저 설정한 뒤 보호·실제 네트워크 바인딩·connect 순서를 따르도록 수정했다. 인증서 검증을 끄거나 상태를 강제로 ACTIVE로 만드는 방식은 사용하지 않았다.

## 검증 방법과 증거 해석

복잡한 구현은 Sol, 독립 검토·빌드·UI/기기 검증은 Luna Max로 분담했다. 검증 중 발견된 문제는 구현 담당자에게 돌려보내고 다시 검사했다.

Android API 36 에뮬레이터 한 대만 사용했다. 읽기 전용 AVD 실행으로 기존 AVD의 영구 상태를 덮어쓰지 않았으며, 가상 CPU 2개와 제한된 메모리를 사용했다. 호스트 CPU affinity와 우선순위도 제한했다. Gradle은 한 번에 하나만, worker 1개로 실행했다. 호스트의 기존 프로그램이나 서비스를 종료하지 않았다.

검증 종료 시 두 VPN과 검사 앱의 종료를 확인했다. 마지막 Android crash 버퍼 출력은 비어 있었다. 이번 작업의 에뮬레이터와 Python fixture 서버를 정상 종료하고 임시 ADB 포워딩을 제거했다. 해당 프로세스와 검사 포트가 남지 않았음을 확인했으며, 종료 후 호스트 `MemAvailable`은 12,198,120KiB였다. 소스·APK·검증 기록은 보존했다.

실제 트래픽은 별도 UID의 `com.luna.deviceprobe`에서 일반 Android 소켓으로 발생시켰다. 이 앱은 `VpnService.protect()`를 호출하지 않는다. 바이트 수만 아니라 결정적인 페이로드의 SHA-256을 비교한다. 장치의 실제 링크 정보에서 TUN, MTU, VPN 포함 여부를 확인한다.

주의해야 할 두 가지 테스트 환경 문제도 기록했다.

- Python UDP fixture의 기본 수신 크기가 8,192바이트여서 큰 에코가 잘리는 문제가 있었다. fixture를 65,535바이트로 수정한 뒤 기준 결과를 다시 측정했다.
- 런처가 없는 초기 검사 앱은 Android의 제한된 패키지 조회에 보이지 않았다. 앱 우회 검사를 위해 검사 앱에 일반 런처 항목을 추가했다. 본 앱에 `QUERY_ALL_PACKAGES`를 추가하지 않았다.

## 아직 일반화할 수 없는 범위와 다음 방향

에뮬레이터의 IPv6 UDP 4,096바이트 전송은 VPN을 끈 상태에서도 타임아웃이었다. 따라서 이 조건을 앱 통과로 표시하지 않는다. IPv6 TCP와 작은 UDP의 실제 TUN 검사, 로컬 IPv6 재조립·체크섬 검사는 각각 별도의 증거다.

물리 기기의 통신사 IPv6-only/NAT64/464XLAT, OEM 절전·백그라운드 정책, 실제 망 품질, 장시간 부하·배터리 소모는 이 에뮬레이터 결과만으로 인증할 수 없다. 기기 모델·Android 버전·통신사별 재현 조건을 확보해 동일한 검사 앱으로 추가 확인해야 한다.

속도 개선의 기준은 동일한 기기·망에서의 직접 연결 대비 지연, 처리량, CPU·메모리·배터리 사용량이어야 한다. 이번 제한된 에뮬레이터의 한 번의 전송 시간으로 “몇 배 빨라졌다”고 주장하지 않는다. 무제한 큐·스레드·재시도나 검증 해제로 숫자를 높이는 방향은 피한다.

배포에는 소유자의 정식 키로 서명한 릴리스와 실제 기기 검증이 필요하다. `app-release-validation.apk`는 로컬 테스트 키로 서명한 검사 용도이며 정식 배포 서명이 아니다. Play 등록·법적 적합성·통신사별 우회 성공을 이 문서가 보증하지 않는다.
