# Tunnel HTTPS 다음 엔진 수정·검증 기록

상태: 최종 빌드·자동 검사·디버그 및 릴리스 APK의 에뮬레이터 실행 검증 완료. 물리 기기·통신사별 검증과 정식 배포 서명은 별도다. 모든 환경에서 버그가 없다는 보증은 아니다.

## 이번 작업의 범위

이 앱은 Android 기기 안에서 패킷을 처리하는 로컬 VPN이다. 해외 서버로 IP를 바꾸는 서비스가 아니며 HTTPS 내용을 복호화하지 않는다. 기존 UI, SNI_MULTI/TLS_SNI_MULTI_V1 전략과 MTU 프로필은 유지한다. 속도를 높이기 위해 체크섬 검사, TLS 인증서 검사, 암호화 DNS 정책을 끄지 않는다.

앞선 IPv4 대용량 UDP, IPv6 조각 처리, 서비스 수명주기 수정은 [이전 구현 기록](IMPLEMENTATION_VERIFICATION_2026-09-05.md)에 따로 남아 있다. 이전 604개 테스트 결과와 이번 결과를 섞지 않는다. 이번 기준 APK와 소스는 [기준 자료](../../benchmark-results/baseline-20260905-1240/)에 보존했다.

## 수정한 문제

### 오래된 UDP 오류와 새 전송이 엇갈리는 경우

소켓에서 예전 요청의 오류가 늦게 도착할 때, 그 사이에 보낸 새 데이터를 예전 오류의 대상이라고 단정하면 안 된다. 기존 코드도 출처가 불분명한 오류에서 이미 보낸 데이터를 재전송하는 것은 막고 있었다. 이번 수정은 여기서 더 나아가, 이미 보낸 데이터는 건드리지 않고 다음 소켓 후보로 넘어가 다음 미전송 데이터를 처리하도록 한다.

테스트는 A와 B를 첫 소켓으로 전송한 뒤 오래된 오류를 의도적으로 도착시킨다. 두 번째 소켓에 A나 B가 다시 전송되지 않고 새 데이터 C만 전송되는지 확인한다. 따라서 이번 결과를 ‘기존 중복 전송 버그를 재현해 수정했다’고 과장하지 않는다.

### 네트워크 전환 중 오래된 DNS 매핑 등록

DNS 응답을 해석하는 동안 Wi-Fi 등의 네트워크 세대가 바뀔 수 있다. 해석 전에 발급한 등록 자격에 네트워크 세대와 내부 세대를 담고, 실제 등록 직전에 다시 검사하도록 했다. 예전 네트워크의 결과가 새 네트워크 상태로 등록되는 것을 막는다.

가상 IP도 폐기 직후 다른 도메인에 재사용하지 않고 일정 시간 격리한다. 늦게 도착한 패킷이 다른 도메인으로 해석될 위험을 줄이는 조치다. 기본 격리는 120초이며, 무한히 늦은 패킷까지 구분하는 보장은 아니다. 사용 가능한 주소가 없으면 억지로 재사용하지 않고 매핑을 거절한다.

### DNS 보안 실패를 우회하는 주소 합성

위조 응답, DNSSEC 오류, 차단·검열·필터링을 뜻하는 EDE를 포함한 응답은 DNS64나 가상 주소 매핑으로 성공 응답처럼 바꾸지 않도록 했다. 여러 EDE가 함께 있거나 형식이 잘못된 경우도 검사한다. 보안 중단 이유가 없는 일반적인 NODATA/REFUSED/SERVFAIL 처리와는 구분한다.

이는 새 사이트 차단 목록을 강제로 추가한 것이 아니다. 기존 DNS 응답에 들어 있는 보안 중단 의미가 대체 경로에서 사라지지 않게 한 것이다.

## 속도 개선과 증명 방법

IPv6 체크섬의 모든 바이트를 검사하는 원칙은 그대로 두고, 합산 작업을 네 갈래로 나누는 작은 변경을 적용했다. 새 소켓 구조나 네이티브 라이브러리는 추가하지 않았다. 틀리면 작은 내부 함수 하나를 되돌릴 수 있는 범위다.

독립적인 느린 계산기와 결과를 비교하는 ShadowTwin 테스트를 추가했다. 홀수·짝수 길이, 경계 길이, 무작위 데이터, 한 비트 변조, 잘못된 범위, IPv6 UDP의 0 체크섬을 검사한다. 테스트용 기준 계산기는 실제 전송마다 중복 실행하지 않는다.

Java 실험에서는 체크섬 계산만 약 1.42~1.72배 빨랐다. 이는 호스트 JVM의 부품 단위 결과이며, 앱이나 인터넷 전체가 그만큼 빨라졌다는 뜻이 아니다. 최종 Kotlin 클래스의 독립 비교와 DIRECT/CURRENT/NEXT 기기 측정은 별도 증거로 남긴다.

최종 Kotlin 비교도 실행했다. 6개 패킷 길이에서 각 10개 준비 배치와 30개 측정 배치를 번갈아 비교했으며, 중앙값 기준 약 1.56~1.61배였다. 32,768바이트 패킷은 약 20.98마이크로초에서 13.47마이크로초로 줄었다. 작은 패킷의 p95는 잡음이 커 모든 꼬리 지연이 좋아졌다고 주장하지 않는다. [원본 결과와 클래스 해시](../../benchmark-results/checksum-final-kotlin-20260905-1344/)에서 정확히 어떤 코드끼리 비교했는지 확인할 수 있다.

| UDP 오류 출처 | 오래된 오류로 이미 보낸 새 데이터를 재전송하는 잘못된 처리 | oldSocketErrorMustNotRetryNewCommittedPayload |

서비스 세대 검사는 고정 시드 3개로 각각 10,000개 사건을 생성한다. 실제 Android에서 30,000회 재연결한 결과가 아니라, JVM에서 순서·소유권 규칙을 검사한 결과다. QUIC Retry 무결성 검사도 기존 회귀 테스트에 유지한다. 이 표는 특정 위협에 대한 증거이지 모든 취약점이 없다는 인증서가 아니다.

## AI 평가: 이기지 못한 후보를 억지로 넣지 않음

기존 TurboAiEngine을 고정 순서 A, 단순 최근 관측 기반 기준 B와 비교했다. 평가 자료는 생성한 시나리오이며 사용자의 방문 기록이 아니다. 360개 평가 표본에서 B의 합성 실패율은 12.5%, 기존 학습기 C는 약 13.89%였다. 이 수치는 실제 인터넷 접속 실패율이 아니다.

판정은 REWORK_C다. 이 평가로 새 AI 정책을 제품에 승격하지 않았다. 데이터나 정답을 바꿔 AI가 이긴 것처럼 만들지 않는다. 기존 학습 기능을 삭제한 것도 아니다. [원본 평가](../../benchmark-results/aegis/aegis-20260905T040448Z/summary.md)에 자료·측정 조건·한계를 남겼다.

추가 검토에서 중요한 제한도 확인했다. 이 시나리오는 720번 모두 새로운 목적지 키를 사용한다. 기존 학습기는 처음 보는 목적지에서 보수적인 순서를 유지하므로 696번은 초기 안전 순서, 24번은 제한된 탐색을 골랐고 일반 학습 활용 단계에 들어가지 못했다. 반면 생성된 정답에는 목적지별 차이가 없어서, 여러 목적지의 기록을 합치는 B가 유리한 조건이다. 정답을 미리 보여 준 누출은 없지만, 이 조건으로 ‘AI 전체가 열등하다’고 결론 내릴 수는 없다.

평가 중에도 이전 결과를 계속 학습하는 순차 평가이므로, 학습을 완전히 멈춘 별도 시험과도 다르다. 다음 연구에서는 현재의 100% 새 목적지 조건을 그대로 보존하고, 재방문·혼합 조건과 목적지별 차이가 있는 조건을 추가해야 한다. 이번에는 제품의 초기 안전 제한을 낮추거나 B로 교체하지 않는다.

## 검증 단계 구분

- P0 수정 후 독립 검사: 49개 suite, 617개 JVM 테스트, 실패·오류·skip 0. lint 오류 0, 경고 6. debug/release APK와 AAB 빌드 성공.
- 위 수치는 체크섬 최종 변경과 주석 정리 전 결과다. 최종 후보의 626개 검사 및 실제 실행 결과는 아래에 별도로 기록한다.
- 실제 트래픽은 별도 UID의 검사 앱에서 발생시키며, 설치된 APK 해시와 실제 VPN 링크를 확인한다. ‘VPN 켬’이라는 라벨만 붙여 측정하지 않는다.
- 동시 연결은 1/8/32개로 제한하고, 한 번에 Gradle 하나와 에뮬레이터 하나만 사용한다. 실패한 표본과 중간 실패 기록도 보존한다.

### 기준 측정에서 추가 발견한 문제

기존 VPN의 32개 동시 HTTP 연결을 반복한 결과, 측정 160건 중 9건이 즉시 연결 실패했다. 직접 연결의 같은 부하에서는 160건 모두 성공했다. 체크섬 수정 APK에서도 동일하게 9건이 실패했다. 이후 확보한 실제 검사 후 진단에 정확히 9건의 `connection-capacity` 오류가 있었다. 단일 연결의 지연·처리량 검사가 통과해도 동시 연결 안정성은 별도라는 뜻이다. 종료된 TCP 연결이 제한된 활성 연결 자원을 계속 차지하는 부분을 수정했으며, 연결 상한만 늘리는 방법은 사용하지 않았다.

검사 도구에서도 집계 문제를 발견했다. 합산 처리량을 계산할 배치 기록이 읽기 단계에서 빠졌고, 인터페이스 MTU 대신 경로의 `mtu 0`이 선택됐다. 진단값도 검사 전 값만 저장해서 검사 후 값과 구분할 필요가 있었다. 실제 링크 원문과 모든 전송 표본은 보존하고 파생 집계를 수정한다. 작은 HTTP 요청이 직접 연결에서도 약 1초 걸리는 현상은 VPN 지연으로 포장하지 않는다.

### TCP 종료 상태 수정과 결과

전송을 완전히 끝낸 연결은 활성 연결 목록에서 즉시 빼고 소켓·버퍼를 정리하도록 변경했다. 늦은 패킷을 구분하는 데 필요한 주소·포트·순서 번호·만료 시각만 작은 종료 기록으로 남긴다. 활성 연결 상한 64개는 유지하고, 작은 종료 기록도 256개로 제한한다. 기록이 가득 차면 기존 제한된 정리 경로를 사용하며 무제한으로 늘리지 않는다.

한쪽만 종료한 연결이나 마지막 확인을 아직 받지 않은 연결은 그대로 보호한다. 같은 주소·포트로 온 새 연결도 아무 요청이나 받아들이지 않고 순서 번호를 비교한다. 오래된 RST가 새 연결을 끊지 못하도록 검사하며, 재전송 SYN 응답에는 바뀌지 않는 최초 순서 번호를 사용한다. 네트워크 전환 뒤 이전 종료 기록이 등록되는 경쟁 상태도 함께 막는다.

TCP 수정 후 JVM 검사 결과는 51개 suite, 626개 테스트, 실패·오류·skip 0이다. 전체 빌드도 성공했다. 동일한 32개 동시 연결의 첫 재검증에서 **160건 모두 성공**했고, 검사 후 용량 초과 거절과 TCP 전달 오류도 0건이었다. 활성 연결은 1개, 작은 종료 기록은 32개로 관찰됐다. [실제 재검증 기록](../../benchmark-results/20260905T050854Z-next-concurrency/summary.md)에 실패 9건이 있던 이전 버전과 구분해 남겼다.

이어 실행한 전체 1·8·32개 동시 연결 검사도 각각 5/5, 40/40, 160/160건 통과했다. 32개 조건은 두 실행을 합쳐 320/320건 성공이다. [전체 동시 연결 검사](../../benchmark-results/20260905T050947Z-next-concurrency/summary.md)에 원본 표본을 연결했다. 부하 종료 뒤 종료 기록이 0개로 정리되고 용량 초과 거절도 0개로 유지되는 [대기 후 진단](../../benchmark-results/20260905T050947Z-next-concurrency/quiescence-diagnostics.json)도 남겼다. 종료 기록을 작게 분리하는 기법은 기존 TCP 구현에도 있는 방법이며, 새 프로토콜을 발명한 것처럼 부르지 않는다.

### 자원 사용을 좋게만 포장하지 않음

32개 동시 연결의 해당 실행에서 앱 프로세스 평균 CPU는 기존 14.544%에서 수정본 13.595%로 관찰됐다. 반면 샘플링한 최대 PSS 메모리는 131,387KiB에서 138,641KiB로 약 7.1MiB 증가했고, 최대 스레드도 158개에서 166개였다. 기존에는 9개 연결이 실패했고 수정본은 모두 성공했다는 차이도 있다. 한 번씩의 실행과 가비지 컬렉션·JIT 영향을 포함하므로 배터리가 절약된다거나 전체 메모리가 줄었다고 결론 내리지 않는다. 버퍼·활성 연결·종료 기록 상한은 계속 유지한다.

## 최종 디버그 APK의 실제 비교표

동일한 API 36 에뮬레이터·로컬 fixture·검사 앱을 사용했다. CURRENT는 보존된 `10d0ee…` APK, NEXT는 TCP 수정까지 포함한 `20465a…` APK다. VPN 비교는 route-all, balanced, MTU 32,768, Turbo 설정 꺼짐으로 맞췄다. Turbo 활성 상태는 별도 기능 검사다.

단일 연결의 전체 전송 속도는 대체로 비슷했다. 10MiB에서는 NEXT가 DIRECT보다 약 2.3%, CURRENT보다 약 1.1% 낮은 표본 결과다. 이를 숨기지 않는다. 확실한 개선은 이번에 재현한 동시 연결 실패 제거와, 별도로 측정한 체크섬 계산 비용 감소다. 합산 처리량은 실패한 전송을 완료 바이트에 넣지 않는다. CPU는 검사 앱이나 기기 전체가 아니라 VPN 앱 프로세스의 표본이며, DIRECT 값은 그 앱이 VPN 없이 머물 때의 비용이다.

작은 요청의 약 1초 지연은 DIRECT에도 있었다. 호스트 자체의 fixture 응답은 매우 짧았고 검사 앱에는 고정 1초 대기가 없었으므로 에뮬레이터 경로 영향을 포함한 결과로 구분한다. 실제 통신사 지연·최대 인터넷 속도·배터리 소모를 이 표로 보장하지 않는다. 메모리·CPU의 작은 차이에 통계적 유의성이 확인됐다고 주장하지 않는다.

원본: [DIRECT 지연](../../benchmark-results/20260905T043102Z-direct-latency/summary.md), [DIRECT 처리량](../../benchmark-results/20260905T043152Z-direct-throughput/summary.md), [DIRECT 동시 연결](../../benchmark-results/20260905T043217Z-direct-concurrency/summary.md), [CURRENT 지연](../../benchmark-results/20260905T043621Z-current-latency/summary.md), [CURRENT 처리량](../../benchmark-results/20260905T043717Z-current-throughput/summary.md), [CURRENT 동시 연결](../../benchmark-results/20260905T043756Z-current-concurrency/summary.md), [NEXT 지연](../../benchmark-results/20260905T051340Z-next-latency/summary.md), [NEXT 처리량](../../benchmark-results/20260905T051429Z-next-throughput/summary.md), [NEXT 동시 연결](../../benchmark-results/20260905T050947Z-next-concurrency/summary.md).

공개 인터넷 요청도 별도로 실행했다. 최종 디버그 APK에서 `https://example.com/`에 10회 준비 요청 후 30회 측정 요청을 보내 모두 성공했다. 이 실행의 p50은 134.5ms, p95는 188.6ms였다. 공개 사이트·단일 시점의 결과이며 이전 버전 대비 속도 개선 주장에는 사용하지 않는다. [공개 HTTPS 원본](../../benchmark-results/20260905T051503Z-next-latency/summary.md)에 요청 조건과 실제 VPN 링크를 남겼다.

실제 서비스 연결·종료 20회와 연속 종료→시작 검사도 통과했다. 연결 세대가 역행하지 않았고 마지막은 generation 43의 connected 상태였다. [수명주기 검사](../../tools/device-probe/results/device-lifecycle-2026-09-05T05-15-26-255Z.json)는 JVM 모의 검사가 아니라 해당 최종 디버그 APK를 제어한 결과다.

## 최종 릴리스 APK 실행 결과

실제 기기에 설치된 릴리스 APK의 SHA-256도 `9a36090f…`로 확인했고, Android가 보고한 활성 VPN 패키지는 `com.tunnelvpn.app`이었다. 디버그 VPN을 켜 놓고 릴리스가 동작한 것처럼 세지 않았다.

MTU 32,768/Turbo 꺼짐, MTU 4,096/Turbo 꺼짐, MTU 4,096/Turbo ACTIVE의 세 구성에서 다음 다섯 검사를 각각 수행해 **15/15개 모두 통과**했다.

- IPv6 HTTP 1MiB 수신: 길이·SHA-256 일치.
- IPv6 TCP 1MiB 왕복: 길이·SHA-256 일치.
- IPv4 UDP 60,000바이트 왕복: 길이·SHA-256 일치.
- IPv6 UDP 1,200바이트 왕복: 길이·SHA-256 일치.
- 공개 HTTPS 요청: TLS 연결 및 HTTP 200 응답 성공.

마지막 Turbo 상태는 desired=true, ACTIVE, operational, transitioning=false였다. 최종 진단의 TCP 용량 초과 거절·전달 오류·패킷 읽기/쓰기 오류는 모두 0이었다. [릴리스 결과와 원본 로그](../../tools/verification-results/2026-09-05-final-release-9a36090f/summary.json)에 설정별 실제 TUN MTU, 바이트 수와 해시를 남겼다. 설치·Activity 실행 성공만으로 네트워크 성공을 판단하지 않았다.

원본의 `duplicateServiceDetected=true`는 숨기지 않았다. 현재 코드에서는 기존 엔진이 있는 상태의 설정 교체도 이 값을 켠다. 이번 두 번의 설정 교체와 `tunnelRestartCount=2`를 함께 해석해야 하며, 두 서비스가 동시에 실행됐다는 증거로 쓰지 않는다. 실제 소유권·세대 검사는 별도로 수행했다.

이전 에뮬레이터 검사에서 IPv6 UDP 4,096바이트 이상은 DIRECT에서도 실패한 환경 한계가 있었다. 이번 작은 IPv6 UDP 통과를 큰 IPv6 UDP까지 통과한 것처럼 확대하지 않는다. 일반 사용자 OS에서의 릴리스 WebView 디버깅 비활성화도 userdebug 에뮬레이터 결과만으로 인증하지 않는다.

## 권한 재시작 문제

권한 변경 전에 생성된 에이전트 세 개의 실제 정책은 on-request/workspace-write로 남아 있었다. 말로 전체 권한을 전달해도 이미 생성된 실행 정책은 바뀌지 않았다. 기존 네 에이전트를 종료하고 새 Sol·Luna를 생성했으며, 새 세션의 never/danger-full-access와 Luna의 승인 없는 ADB 실행을 확인했다. 코드와 기존 증거는 삭제하지 않았다.

요청한 대로 앱 소스와 작성한 검사 도구의 일반 주석은 Luna가 제거했고, 새 코드에도 일반 주석을 추가하지 않았다. 실행에 필요한 shebang·컴파일러 지시·법적 고지와 문자열 안의 URL은 삭제 대상이 아니다. 설명은 README와 별도 기술 문서에 남겼다. 주석 정리 후 전체 검사와 스크립트 문법·UI 검사를 다시 확인했다.

## 최종 정리

최종 JVM 626개, UI 실행 2개, 측정 도구 회귀 검사 2개가 통과했다. lint 오류는 0개, 경고는 6개다. 독립 Luna 감사에서도 문서의 수치·파일 경로·APK 해시와 원본이 일치함을 확인했다.

마지막 Android crash 버퍼는 비어 있었다. 검사 완료 후 이번 에뮬레이터의 두 VPN 앱과 검사 앱을 종료하고, 임시 ADB 포워드 18333을 제거했다. 이번에 띄운 에뮬레이터 PID 1567183과 fixture PID 1585203만 정상 종료했다. 해당 프로세스, 검사 포트 18080/18081/18082/18333, 연결된 에뮬레이터와 임시 포워드가 남지 않았음을 확인했다. 호스트의 사용 가능한 메모리는 12,484,824KiB, 약 11.9GiB로 돌아왔다.

기준·중간 실패·최종 결과 파일은 삭제하지 않았다. 최종 소스 묶음과 현재 파일의 비교도 일치했고, 정리 후 APK/AAB 해시를 다시 확인했다. 완료된 서브에이전트도 모두 종료했다.

## 아직 증명하지 못한 범위

실제 통신사 NAT64/464XLAT, 삼성 등 OEM 절전 정책, 물리 기기의 배터리·발열, 2/6/12시간 안정성은 에뮬레이터 검사로 대체하지 않는다. [물리 기기 검사표](NEXT_ENGINE_PHYSICAL_MATRIX.md)에 재현 조건과 필요한 증거를 명시했다.

FlowSeal·Path Genome·네이티브 배치 I/O 같은 대규모 구조 변경은 구현 완료 기능이 아니다. 작은 체크섬 최적화를 새로운 프로토콜 발명이라고 주장하지 않는다. 실측 근거가 없는 구조 확장은 이번 안정화 결과와 분리한다.

최종 배포에는 소유자의 정식 서명 키가 필요하다. 로컬 테스트 키로 서명한 릴리스 APK는 설치·축소 코드 검사용이지 정식 배포 서명이 아니다.
